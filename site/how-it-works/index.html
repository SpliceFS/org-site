How SpliceFS works

Picture the same folder of files on three servers. SpliceFS lets a computer open that folder as if it were on its own disk, and it pulls every file from all three servers at once.

This page follows one file from the servers to the program that reads it, in four steps. Then it lists what SpliceFS cannot do yet, and where it is going.

1

You have the same files on a few servers

Each server keeps the files as ordinary files in an ordinary folder. A small program, splicefsd, serves them. You keep the folders the same with the sync tool you already use, for example Syncthing or rsync.

Then you pick one host name for the whole group, for example files.example.com, and point it at one or more of the servers. That name is all a reader ever has to know.

  • SpliceFS does not copy files between servers today. Your sync tool does. That is the dashed line in the picture.
  • The pictures call the servers node-1, node-2 and node-3.
2

The reading computer finds the servers

On the computer that reads, the client program splicefs logs in at that one name, over HTTPS, with a user name and a password. The server that answers hands back the address of every server in the group. From then on the client talks to each server directly.

  • Servers can come and go. The client asks for the list again every minute, so you add or remove a server without touching any reader.
  • The users and the server addresses are kept in small files that your sync tool carries along with everything else.
3

Opening a file pulls it from every server at once

When you open a folder, the client asks every server what is in it and shows you one combined list. When you open a file, the client cuts it into blocks of 5 MiB and asks a different server for each block, all at the same time. As the blocks arrive it puts them in order and hands them to the program that is reading.

That is where the speed comes from: three servers together deliver about three times what one could, as long as the line of the reading computer keeps up.

  • A second read is local. Blocks are kept in a cache on the local disk, so reading the same part again does not touch the network.
  • A file is only asked from the servers that have it.
  • Small files, and small reads in the middle of a file, are fetched directly and are not cached.
4

A server drops out and the read keeps going

When a server is slow or stops answering, the client asks another server for the same block and takes whichever complete answer comes first. The program that is reading sees nothing, and the folder stays mounted.

  • The server gets its work back. A slow server is given less to do. A failed one is rested, one second at first and thirty at most, then tried again, so it carries its share as soon as it recovers.
  • A server whose copy of a file has changed is left out for that file.
  • If no server at all can deliver a block within the time limit, the read fails with an error. It does not hang.

What it cannot do yet

SpliceFS is new, and it is better to know the limits before you try it.

By design, for now
  • You cannot write. The folder is read-only.
  • It does not copy files between servers. Your sync tool does that.
  • Files must arrive whole. A file has to appear in a share complete: written under a temporary name and renamed at the end, as Syncthing and rsync do by default. A file that is written in place can be served half-written, and with two servers a half-written copy with a newer time is used in place of the complete one.
Rough edges
  • Removing a user takes a moment to bite. A user who is removed or disabled loses access within 30 seconds, also while logged in.
  • A new login needs a moment. A login made at one server is refused by the others until your sync tool has delivered that server's node file to them.
  • Starting with every server down. A client that starts while no server can be reached cannot list folders, although the file contents it read before are still in its cache.

On a Mac the folder is mounted through a small NFS server that is part of the client; Linux and FreeBSD use FUSE. The Mac way has limits of its own: a read that has to wait longer than about 9 seconds fails, speed stays below Linux because requests are handled one at a time per connection, and after an outage a new file name can look missing for up to 30 seconds.

For how this stands next to other systems, see How SpliceFS compares.

Where it is going

Plan, not built. Reading is step one. Everything below is where the project is headed. None of it exists yet, and details will change.

Solid outline = exists today. Dashed outline = planned.

Writing that happens everywhere, or not at all Planned

You will be able to write through the folder. A change to a file is a transaction: every server that holds the file takes it, or none does. You never end up with half a change.

Servers that cover for each other Planned

A cohort is a group of servers that hold data together, the way the disks of a RAID set do. Lose one member and the data is still complete. Reads are spread over the members.

Locks that every reader respects Planned

When a program locks a file through one client, every other client honors that lock, wherever it is. The goal is full POSIX behavior, so ordinary programs work on a SpliceFS folder without changes.

The same from anywhere, and a say in where data lives Planned

A client on the local network, one over a VPN and one over the public internet should all be treated the same way. And a rule on one file, one folder or a whole cluster will say at which locations that data is held.

The road by version Planned

0.x is the core of the SpliceFS protocol, and access controls. 1.x is enterprise tooling and visibility. 2.x: only time will tell.
