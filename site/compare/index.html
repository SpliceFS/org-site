How SpliceFS compares

SpliceFS aims to become a complete distributed filesystem. Today it is step one of that road: a read-only share where a reader pulls the same files from several servers at once. The other systems on this page are mature. This page says plainly what each one aims to be, and how far along it is.

Where SpliceFS is today

  • It is alpha software. The first 0.x versions are published; none has run in production.
  • It has never run in production. Its own tests are the only proof that it works.
  • Its protocol and its configuration may still change.
  • It only reads. Writing, file locks and keeping copies in step are plans, not features.
  • Its access control is basic: users with a password and a list of shares.
  • Nobody outside the project has reviewed its security, and no speed measurements are published.
  • It runs on Linux and macOS. There is no Windows version.

It does not replace any system on this page today. If you need something to depend on now, use one of them.

Where SpliceFS is headed

Read-only is step one. None of the following exists yet; it is what the project is building toward.

  • Read and writeChange files through the mount, not only read them.
  • CohortsGroups of servers that hold redundant copies, like RAID.
  • Transactional file changesA change is applied completely or not at all.
  • Distributed file locksLocks that hold across every server and every client.
  • Full POSIX behaviorPrograms see what they would see on a local disk.
  • Local and remote clients alikeThe same service on the local network, over the public internet or over a VPN.
  • Geographic tenancyChoose where data lives, for a file, a directory or a whole cluster.

The plan by version

  • Versions 0.xThe core of the SpliceFS protocol, and access controls.
  • Versions 1.xEnterprise tooling and visibility.
  • Versions 2.xOnly time will tell.

These are plans, not features. The 0.x line has started: its first versions are published as packages.

What is built so far

The design keeps to three aims. The grey lines say what is still missing.

  • Lean

    • One program on each server and one on the reader.
    • No database, no cluster manager, no quorum.
    • The server keeps nothing about its readers.
    • One server is a valid cluster.
    • Today lean also means less: no writes, no replication, no locking yet.

  • Standard

    • Everything travels over HTTPS.
    • Folder listings are JSON. File contents are ordinary HTTP byte ranges.
    • Every request can be repeated with curl.
    • The API on top of HTTPS is its own, and it is not frozen yet.

  • Secure

    • TLS is on from the first start.
    • Passwords are stored as Argon2id hashes.
    • A login gives a short-lived signed token, limited to the shares that user may read.
    • The server never writes to a share.
    • No outside security review yet.
    • A token cannot be revoked before it expires, 30 minutes by default.

When to use something else

Today, in most cases. Use NFS or SMB for a normal shared folder. Use CephFS or GlusterFS when the storage system itself must keep copies in step. Use Syncthing or Resilio Sync to keep full copies of a folder on several devices. Use Rclone to reach cloud storage. Use BitTorrent to hand a fixed set of files to many people. SpliceFS is worth a look today only if you want to read the same live folder from several servers at once across the internet, and you can accept alpha software.
